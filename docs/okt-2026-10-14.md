## Feil vi traff

### Feil 1 – `-o was unexpected at this time` (steg 6)

- **Symptom:** `Setup-Oidc.ps1` stoppet på `az identity federated-credential list ... --query "length([?name=='gh-dev-plan'])"` med exit code 255.
- **Årsak:** `az` på Windows er en batch-fil (`az.cmd`) som kjøres av cmd.exe. PowerShell 7 sender argumenter uten anførselstegn når de ikke inneholder mellomrom. cmd.exe ser da parentesene i `length(...)` og tolker dem som egen syntaks. Runbookens tips om å unngå pipe var ikke nok – parenteser gir samme problem.
- **Løsning:** Spørringer uten parenteser, f.eks. `--query "[?name=='gh-dev-plan'].name" -o tsv`, og sjekk om resultatet er tomt i PowerShell (`if (-not $r)`). Rettet på tre steder i scriptet.
- **Lærdom:** Scriptet er idempotent, så det kunne trygt kjøres på nytt etter rettelsen. Det som allerede var opprettet (RG, identiteter), ble bare hoppet over.

### Feil 2 – `AADSTS700213` med ID-er i subject (steg 8)

- **Symptom:** `azure/login` feilet: *No matching federated identity record found for presented assertion subject `repo:tleirbakken@58067749/avd-iac@1419648460:environment:dev-plan`*.
- **Årsak:** GitHub sender nå subject med **uforanderlige ID-er** for eier og repo. Det beskytter mot at noen sletter et repo, lager et nytt med samme navn og arver tilliten til Azure. FIC-en var laget med det gamle formatet `repo:tleirbakken/avd-iac:environment:dev-plan`.
- **Diagnose:** `azure/login`-loggen viser eksakt hva GitHub sender, under *Federated token details → subject claim*. ID-ene ble bekreftet med `gh api repos/tleirbakken/avd-iac`.
- **Løsning:** `Setup-Oidc.ps1` henter ID-ene fra `gh api` og bygger subject som `repo:<owner>@<ownerId>/<repo>@<repoId>:environment:<env>`. Finnes FIC-en med feil subject, blir den oppdatert (før ble den bare hoppet over).

### Feil 3 – `AuthorizationFailed ... write` i preflight (steg 8)

- **Symptom:** Innlogging OK, men `az deployment sub validate` feilet på `resourceGroups/write`, `deployments/write` og `storageAccounts/write`.
- **Årsak:** Standard `--validation-level` er `Provider`, som sjekker at identiteten har **skrive**-RBAC for alle ressurser i malen. Plan-identiteten er bevisst read-only.
- **Feil løsning (fra runbooken):** Legge actions til i custom role. Det ville gitt plan-identiteten skrivetilgang og brutt sikkerhetsmodellen.
- **Riktig løsning:** `--validation-level ProviderNoRbac` på `validate` og `what-if` i Plan-jobben. Full validering mot resource providers, men RBAC sjekkes bare for lesing. Deploy-jobben beholder standard, med full RBAC-sjekk.

## Spørsmål og svar

### Hvorfor er steg 3 merket Claude Code – står det ikke i runbooken?

Steg 3 står i runbooken, men inneholder ikke selve filene. Det består av tre ting: lagre runbooken som `docs/runbook.md`, starte Claude Code og gi den en ferdig prompt. Filene står i **Vedlegg A** nederst i samme dokument, og steg 3 peker dit.

Steget er merket Claude Code fordi det er mekanisk kopiering av 10 filer til riktige stier pluss syntakssjekk – kjedelig og lett å gjøre feil manuelt (feil sti, YAML-innrykk, manglende fil). Alt som endrer Azure eller GitHub (push, OIDC, deploy) gjøres av deg, slik [CLAUDE.md](../CLAUDE.md) sier under «Arbeidsregler».

### Hva står FIC for?

**Federated Identity Credential.** En tillitsregel på en managed identity (eller app registration) i Entra ID: «Godta et token fra denne eksterne utstederen, men bare når innholdet matcher nøyaktig.»

| Felt | Verdi her | Betydning |
|---|---|---|
| `issuer` | `https://token.actions.githubusercontent.com` | Hvem som utsteder tokenet (GitHub Actions) |
| `subject` | `repo:tleirbakken@58067749/avd-iac@1419648460:environment:dev` | Hvilket repo og environment tokenet må gjelde |
| `audiences` | `api://AzureADTokenExchange` | Hvem tokenet er ment for (Entra sin token-utveksling) |

Flyten i en kjøring:

1. Jobben `Deploy dev` starter med `environment: dev`.
2. GitHub lager et kortlivet OIDC-token med subject for `environment:dev`.
3. `azure/login` sender tokenet til Entra og ber om et Azure-token for clientId-en til `id-gh-avd-iac-dev`.
4. Entra sjekker FIC-en. Matcher issuer, subject og audience, utstedes et Azure-token. Ellers: `AADSTS700213`.

**Hvorfor null secrets:** Det finnes ikke noe passord eller sertifikat som kan lekke. Tilliten bygger på at GitHub signerer tokenet og at subject matcher.

**Sikkerhetspoenget:** Subject inneholder environment-navnet, og `dev` er låst til `main`. En PR-branch kan bare få et token for `dev-plan`, som bare matcher lese-identiteten. Derfor to identiteter med hver sin FIC.

### Hva er CorrelationId i output fra `az deployment sub validate`?

En unik ID (GUID) som Azure Resource Manager gir hver forespørsel. Alle underliggende operasjoner (ARM og resource providers) får samme ID. Den gjør ingenting i seg selv, men er nøkkelen når noe feiler:

| Situasjon | Bruk |
|---|---|
| Se detaljer om en feil | Activity Log (portal: Subscription → Activity log → filtrer på Correlation ID), eller `az monitor activity-log list --correlation-id <id>` |
| Policy-deny | Activity Log-oppføringen viser hvilken policy-tildeling som slo til |
| Supportsak hos Microsoft | Det første de spør om |
| Pipeline-feil | Feil fra `az deployment` i Actions har også en CorrelationId, så feilen kan spores fra loggen til Azure |

### Hvor ser jeg validate i GitHub?

Det finnes to ting som heter «validate»:

| Hva | Hvor | Hva den gjør |
|---|---|---|
| Jobben **Validate** | Første boks i kjøringen | `az bicep lint`, `build` og `build-params`. Syntaks og linter, uten Azure. |
| Steget **Preflight-validering** | Inne i jobben **What-if** | `az deployment sub validate`, samme som lokalt i steg 4. Krever Azure-innlogging. |

Slik finner du dem: **Actions** → klikk kjøringen → grafen viser **Validate → What-if → Deploy dev** → klikk en jobb for å se stegene og loggen.

### Skal du se noen av verdiene i Settings (steg 7)?

Nei. Scriptet viste allerede alle verdiene, og ingen kommandoer feilet. Steg 7 er en visuell kontroll for din egen del. Det som er verdt å bekrefte – fordi sikkerhetsmodellen hviler på det – er at `dev` er låst til `main`. Det kan sjekkes fra terminalen:

```powershell
gh api repos/$GH/environments/dev --jq '.deployment_branch_policy'
gh api repos/$GH/environments/dev/deployment-branch-policies --jq '.branch_policies[].name'
gh secret list --repo $GH
```

### PR-en sier «This branch was successfully deployed» – er noe deployet?

Nei. GitHub registrerer hver jobb som bruker `environment:` som en «deployment» til det environmentet. Det som vises, er What-if-jobben mot `dev-plan`. Ingenting ble opprettet i Azure før merge til `main`.
